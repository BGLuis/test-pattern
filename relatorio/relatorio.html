1 Padrões de Criação de Dados: Object Mother e Data Builder

Na construção da suíte de testes de src/services/CheckoutService.js, os cenários de negócio dependem da composição de entidades de domínio (User, Item e Carrinho). Para prevenir o Test Smell de Setup Obscuro (Obscure Setup) desde o início, combinamos dois padrões complementares de criação de massa de testes em __tests__/builders/: o Object Mother (UserMother.js) e o Data Builder (CarrinhoBuilder.js).

1.1. Por que CarrinhoBuilder foi usado em vez de um CarrinhoMother?

Foco na Variação Combinatória vs. Entidades Estáticas

O padrão Object Mother é ideal para objetos simples com poucas variações fixas e estáveis entre testes. É o caso de User, cujo domínio possui essencialmente dois perfis relevantes (PADRAO e PREMIUM), atendidos diretamente por UserMother.umUsuarioPadrao() e UserMother.umUsuarioPremium().

Já o Carrinho é um agregado composto por múltiplas dimensões independentes: o comprador (padrão ou premium), a quantidade de itens, os valores individuais para validar cálculos de desconto (ex.: R$ 200,00) e estados limítrofes (carrinho vazio). Modelar essas combinações com um CarrinhoMother provocaria uma explosão combinatória de métodos estáticos (umCarrinhoPadraoComUmItem(), umCarrinhoPremiumDe200Reais(), umCarrinhoVazio(), etc.), tornando a classe de apoio rígida e difícil de estender. O Data Builder resolve esse problema fornecendo valores padrão válidos no construtor e uma API fluente (.comUser(), .comItens(), .vazio(), .build()) para sobrescrever apenas o que importa em cada teste.

1.2. Comparativo Prático: Setup Manual ("Antes") vs. Data Builder ("Depois")

× Antes: Setup Manual Complexo (Obscure Setup)
// Teste poluído com detalhes estruturais irrelevantes
const usuario = new User(
  2,
  'Usuário Premium',
  'premium@email.com',
  'PREMIUM'
);
const item1 = new Item('Suporte Notebook', 120);
const item2 = new Item('Headset', 80);
const carrinho = new Carrinho(usuario, [item1, item2]);

// Mesmo para testar apenas falha no pagamento:
const uFail = new User(1, 'A', 'a@a.com', 'PADRAO');
const cFail = new Carrinho(uFail, [new Item('X', 50)]);
✓ Depois: Object Mother + Data Builder Fluente
// Cenário Premium: destaca apenas usuário e total (R$ 200)
const usuarioPremium = UserMother.umUsuarioPremium();
const carrinho = new CarrinhoBuilder()
  .comUser(usuarioPremium)
  .comItens([
    new Item('Suporte Notebook', 120),
    new Item('Headset', 80),
  ])
  .build();

// Cenário de falha de pagamento: defaults ocultam ruído
const carrinhoFalha = new CarrinhoBuilder().build();
// Cenário de borda: intenção explícita
const carrinhoVazio = new CarrinhoBuilder().vazio().build();

1.3. Benefícios em Legibilidade e Manutenção

  • Destaque da Regra Sob Teste (Relevance): O bloco Arrange comunica imediatamente a pré-condição do cenário. No caso de falha no pagamento, o leitor não precisa decifrar usuários ou itens arbitrários; no cenário Premium, somente o perfil do usuário e o montante de R$ 200,00 ficam explícitos.
  • Baixo Acoplamento aos Construtores de Domínio: Caso a assinatura de User ou Carrinho receba novos parâmetros obrigatórios (como CPF ou moeda), a alteração fica isolada dentro de UserMother e CarrinhoBuilder, evitando a quebra em cascata de dezenas de testes (prevenção de Fragile Tests).
  • Segurança Contra Estado Compartilhado: A implementação de comItens(itens) realiza cópia defensiva ([...itens]), e cada chamada a new CarrinhoBuilder() cria instâncias independentes, preservando o isolamento entre execuções.

2 Padrões de Test Doubles: Stubs vs. Mocks na Prática

O serviço CheckoutService recebe três colaboradores externos via injeção de dependência: GatewayPagamento, PedidoRepository e EmailService. Em suas implementações concretas, todas lançam exceção caso invocadas diretamente. Para testar a lógica de negócio de forma determinística e sem I/O real, aplicamos Test Doubles (conforme taxonomia de Gerard Meszaros e Martin Fowler) utilizando funções simuladas do Jest (jest.fn()).

2.1. Estudo de Caso: Teste de "Sucesso Premium" (Etapa 5)

it('deve aplicar desconto de 10% na cobrança e enviar e-mail de aprovação (Stub + Mock)', async () => {
  // Arrange
  const usuarioPremium = UserMother.umUsuarioPremium();
  const carrinho = new CarrinhoBuilder()
    .comUser(usuarioPremium)
    .comItens([new Item('Suporte Notebook', 120), new Item('Headset', 80)])
    .build();
  const gatewayStub = { cobrar: jest.fn().mockResolvedValue({ success: true }) };
  const repositoryStub = {
    salvar: jest.fn().mockImplementation(async (p) => new Pedido(1, p.carrinho, p.totalFinal, p.status)),
  };
  const emailMock = { enviarEmail: jest.fn().mockResolvedValue() };
  const checkoutService = new CheckoutService(gatewayStub, repositoryStub, emailMock);

  // Act
  const pedido = await checkoutService.processarPedido(carrinho, '9999-8888-7777-6666');

  // Assert (Verificação de Comportamento e Estado)
  expect(gatewayStub.cobrar).toHaveBeenCalledWith(180, '9999-8888-7777-6666');
  expect(emailMock.enviarEmail).toHaveBeenCalledTimes(1);
  expect(emailMock.enviarEmail).toHaveBeenCalledWith(
    'premium@email.com', 'Seu Pedido foi Aprovado!', 'Pedido 1 no valor de R$180'
  );
  expect(pedido.totalFinal).toBe(180);
});

2.2. Identificação dos Dublês e Verificação de Estado vs. Comportamento

GatewayPagamento & PedidoRepository como Stubs

Papel no teste: Fornecer respostas pré-programadas (canned answers) que controlam o fluxo de execução do SUT: gatewayStub retorna { success: true } para autorizar o avanço do checkout, enquanto repositoryStub devolve um Pedido persistido com id = 1.

Por que são Stubs: Sua função primária é viabilizar a Verificação de Estado sobre o valor retornado pelo método (pedido.totalFinal === 180 e pedido.status === 'PROCESSADO'). Embora o teste também verifique o argumento 180 passado a cobrar() para comprovar que o desconto ocorreu antes da cobrança, o foco do gateway é atuar como fornecedor de resposta do caminho feliz.

EmailService como Mock

Papel no teste: Registrar a chamada efetuada pelo CheckoutService e permitir asserções estritas sobre como a interação ocorreu (toHaveBeenCalledTimes(1) e toHaveBeenCalledWith(...)).

Por que é um Mock: O envio de e-mail é um efeito colateral (side effect) puro: seu retorno não é utilizado pelo chamador e eventuais falhas são silenciadas em um bloco try/catch dentro de processarPedido. Como não há nenhum estado no objeto Pedido que ateste se a notificação foi disparada para premium@email.com com o texto esperado, somente a Verificação de Comportamento (inspeção de interação) garante essa regra.

Tipo de Dublê Dependência no Projeto Objetivo Principal Estratégia de Verificação
Dummy repositoryDummy / emailDummy (falha de pgto) Preencher parâmetros obrigatórios sem serem invocados Sem asserções sobre o dublê ({})
Stub gatewayStub, repositoryStub, emailStub (erro SMTP) Fornecer respostas ou rejeições controladas para conduzir o fluxo Estado: expect(pedido).toBeNull() / .toBe(180)
Mock emailMock (sucesso) e mocks negativos na falha Validar contratos de saída e ausência de chamadas indevidas Comportamento: toHaveBeenCalledWith / not.toHaveBeenCalled

3.2. Conclusão: Prevenção de Test Smells e Sustentabilidade da Suíte

Ao contrário da abordagem puramente reativa de detectar e corrigir Test Smells após a degradação do código, a aplicação deliberada de Padrões de Teste atua na raiz preventiva da qualidade. O uso combinado de UserMother e CarrinhoBuilder elimina a repetição de blocos de inicialização verbosos e evita o Obscure Setup e o Fragile Test diante de evoluções no modelo de domínio. Cada caso de teste segue estritamente a estrutura Arrange-Act-Assert (AAA), expondo apenas os dados que justificam o comportamento verificado.

Simultaneamente, a separação consciente entre Dummies, Stubs e Mocks impede o acoplamento da suíte a gateways financeiros, bancos de dados ou servidores SMTP reais, garantindo testes rápidos e 100% determinísticos. Ao reservar Mocks apenas para interações e efeitos colaterais essenciais (como o disparo do EmailService e a garantia de não persistência em falhas) e usar Stubs para verificação de estado nos demais colaboradores, evita-se também o excesso de especificações frágeis (overspecification), resultando em uma suíte legível, confiável e sustentável ao longo do ciclo de vida do sistema.
